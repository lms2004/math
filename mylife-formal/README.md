# MyLife 设计的形式化验证（Lean 4）

这个包里有两样东西：

* `design/`：MyLife 设计文档。`MyLife-design.txt` 是在你的原文上最小改动后的版本，
  `MyLife-design-original.txt` 是原文，`CHANGES.md` 逐条说明改了哪 15 处、为什么，`MyLife-design.diff` 是逐字对比；
  `CONTRACT.md` 是操作接口契约：每种写入谁能发起、写入前检查什么、哪些视图由数据推出。技术设计照着它实现。
* `MyLife/`：把设计的核心思想和核心原则抽成形式化性质，在 Lean 4 里建模并证明。

全部证明都经过 Lean 内核检查，没有 `sorry`，只依赖 Lean 的标准公理（`propext`、`Quot.sound`，
有两条用到 `Classical.choice`）。`lake build` 时会打印每条定理用到的公理（见 `MyLife/Audit.lean`）。

## 结论

**可以。** 设计里大部分硬性要求是“安全性质”（坏事永远不发生）或“不变量”（每个状态都满足），正好适合形式化。
目前证明了 51 条主要定理，另有 4 个反例和 12 个示例，都由 Lean 直接检查。

这些性质分三类：

| 类别 | 例子 | 能做到什么 |
|---|---|---|
| 结构和流程性质 | 只追加、可追溯、只有我能拍板、世界不引用个人、同一问题只有一个有效节点、冲突不悄悄改值、吸收幂等 | **完整证明**：对所有合规状态成立，也对任意 AI 输出成立 |
| 依赖判断的性质 | “是不是同一个问题 / 同一个对象 / 同一笔钱”、作者是谁、属于世界还是个人 | **相对证明**：把判断当作显式的键或记录，证明程序在这些判断之上正确。判断本身对不对，模型管不到 |
| 语义质量 | 整理没改变意思、程度标得对、信息密度、AI 理解得对 | **不能形式化**：只能证明它们的结构性替代条件（例如“确定”必须引用直接依据），其余靠过目 |

形式化发现了 4 个原设计没写明、但不变量必须依赖的守卫，以及几处需要你拍板的语义选择。
你的决定已经写进模型和设计文档（见第 4 节）。

## 1. 合适的结构：只追加的写入日志 + 推出的视图

设计里的“只追加”“推出”“任意时刻都能还原”放在一起，其实就是事件溯源（event sourcing）：

```
          MCP 写入 ──► 程序检查 CheckP ──► 通过才追加
                                              │
        ┌─────────────────────────────────────▼─────────────────────────────────┐
        │  日志：原件 · 片段 · 事实 · 作废 · 版本 · 结束 · 移层 · 关联 · 稿子 ·   │
        │        吸收记录 · 确认 · 作者更正 · 删除记录 ……（按写入时间排列，只追加）│
        └──────┬──────────────┬───────────────┬──────────────┬─────────────────┘
               ▼              ▼               ▼              ▼
          Current Model   事实当前值、冲突   过目事项（引用没跟上、  界面投影 / 统计
            (推出)       被盖过的说法(推出)  作者被更正）(推出)     (推出，不写回)
```

* 模型里把所有只追加的存储按写入时间合成一条日志 `Log`。这是证明手段，实现可以继续分目录存，
  只要每个存储都只追加、视图都由它们算出来。
* 文字（原件内容、句子文本）放在仓库外的内容寻址库里，日志里只有哈希和指纹。
  所以所有检查和定理都不依赖文字内容：按你的要求删除内容（唯一的例外）不会破坏任何已证明的性质，
  出处会指向一个只剩 id 的删除记录。
* 写入前由程序检查（`CheckP`，对应设计里“记录与检查”那一节），不合规就拒绝。
  合规状态 `Reachable` = 从空日志开始、每一步都通过检查得到的日志。

## 2. DAG 在哪里

| 图 | 是 DAG 吗 | 为什么 | 定理 |
|---|---|---|---|
| 存储层引用图：每条写入 → 它引用的更早写入（出处片段、事实、理由、被引用节点在写入那一刻的版本……） | **是，对任意日志都是** | 引用在写入时解析到已经写入的东西，写入时间本身就是拓扑序（和 Git 的提交图一样） | `storage_acyclic` |
| 层级：个人认知模型 → 世界模型 → 原始依据层 | **是** | 需要检查：写入时引用方向正确，**并且移层时也要检查** | `layerInv` |
| 节点来源：分裂、合并、阶段接续 | **是** | 来源节点必须已经存在 | `lineage_acyclic` |
| 活视图的节点引用图（按 id 取最新版本） | **不是，也不需要是** | A 引用 B，之后 B 的新版本引用 A，两步都合规 | `live_graph_may_cycle` |

所以 DAG 不是要额外去验证的结构，而是“只追加 + 引用在写入时解析”的直接结果。
活视图里的环不会造成传播死循环：节点“变了”只能来自你写的认知版本或结束（`node_change_by_me`），
每传一层都要经过你。

## 3. 性质清单

“逐条写入”的性质只要每条写入在当时通过检查、加上“查到的东西永远查得到”就成立；
“全局不变量”要对整个状态做归纳，往往需要额外的守卫。

### 只追加与还原（核心原则 1）

| 性质 | 定理 |
|---|---|
| 每次合规写入后，旧日志原样是新日志的后缀；事实、片段、版本各自也只追加 | `step_suffix`、`records_suffix`、`versions_suffix` |
| 时刻 t 的快照（以及由它推出的任何视图，包括 Current Model）不会被之后的写入改变 | `snap_append`、`view_stable`、`currentNode_at_time_stable` |
| 每个历史快照本身也是合规状态：所有不变量在每个历史时刻都成立 | `reachable_snap`、`invariant_at_every_time`、`layerInv_at_every_time` |

### 只有我能拍板（核心思想 4、Agent 的边界）

| 性质 | 定理 |
|---|---|
| 新建、新版本、结束、移层、确认不用改、冲突裁决、定权威作者、删除、作者更正，这些写入的发起者都是我；Agent 只能存原件、记账、抽取 / 作废事实、追加来源、挂关联、起草稿子 | `only_me_decides` |
| 每个认知版本（新建节点的第一个版本除外）都有理由，理由是写入那一刻已经存在的我的话 | `cognitive_has_reason` |
| 决定的结论和承诺都在那次写入的逐句确认清单里 | `decisions_confirmed` |

### 可追溯、看得出谁起草（核心思想的目标、核心原则 2）

片段的作者可以更正（你的决定），所以和作者有关的性质分两层：写入那一刻一定成立；之后作者被更正的，一定进过目。

| 性质 | 定理 |
|---|---|
| 每条事实、每个追加的来源，出处片段都在它之前存在；写入那一刻作者是我或外部发布者，**不是 AI，也不是作者不明** | `facts_traceable_not_ai`、`added_sources_not_ai` |
| 任何版本（含历史版本）的每一句：出处先于版本存在；写入那一刻来源类别（原话 / 整理 / AI 起草）有定义；引用的东西都存在 | `sentence_traceable` |
| 写入那一刻：AI 起草的句子都标了程度；标“确定”的至少引用一处直接依据（事实或我的话）；我的原话和整理不标程度 | `degree_rules` |
| 来源类别只会因为作者更正而改变 | `drafter_changes_only_by_correction` |
| **作者更正后不漏**：任何一句，要么按现在的作者看仍满足全部正文规则，要么进过目；任何事实，出处现在的作者要么仍是我或外部，要么进过目 | `sentence_ok_now_or_flagged`、`fact_ok_now_or_flagged` |
| 一句话只有一个出处（“整理只在一个片段内进行”）；事实的结构里没有指向节点的字段（依据不引用认识） | 由类型保证 |

### 分层（世界模型 6）

| 性质 | 定理 |
|---|---|
| 有效的世界节点，当前版本引用的节点都在世界模型（移层可以成组进行） | `layerInv` |
| 移层被挡住时，程序列出的正是挡住它的引用者 | `moveBlockers`（示例 `move_blockers_listed`） |
| 个人认知模型的变化牵动不到世界节点 | `world_not_stale_by_personal` |
| 认识层的写入不改变片段、事实记录和任何事实的当前值（认识变了不回头改依据） | `evidence_unaffected_by_cognition` |

### 不重复（核心原则 3）

| 性质 | 定理 |
|---|---|
| 原件按内容哈希只存一份，再存只追加保存记录 | `sources_unique` |
| 片段 id 唯一 | `fragInv` |
| 同一个问题只有一个有效节点；“任何时刻只有一个有效阶段节点”是它的特例（阶段节点都回答“我现在处于哪个阶段”） | `uniqueInv` |
| 同一身份、同样的值，没作废的事实记录只有一条；别的作者说同样的值只追加来源 | `factUnique` |

### 事实的当前值（原始依据层 · 事实）

| 性质 | 定理 |
|---|---|
| 第一个值直接成为当前值；同一作者的新值接替旧值；权威作者的新值接替 | `first_value`、`same_author_supersedes`、`authority_supersedes` |
| 没定权威作者时，另一个作者的不同值标为冲突，当前值不变 | `conflict_keeps_current` |
| 定了权威作者以后，其他作者的不同值不改当前值、不提出冲突，但列进“被盖过的说法”，查得到 | `authority_overrides_listed` |
| 当前值成为当前值的那一刻，出处是我或外部发布者，不是 AI 的话 | `current_not_ai` |
| 有待裁决的冲突时，任何不是我发起的写入都不会让它消失 | `conflicts_only_me` |

### 更新的传播

“哪些引用没跟上”不存，由日志推出（`Stale`）。

| 性质 | 定理 |
|---|---|
| 不漏：节点有了新的认知版本、或事实当前值变了，所有直接引用它的有效节点都进过目 | `cognitive_version_flags_citers`、`fact_change_flags_citers` |
| 不多：我确认“不用改”之后不再提醒；整理版本、挂关联、追加来源、稿子不触发 | `ack_clears`、`quiet_no_new_stale` |
| 只提醒不改写，传播每一层都经过我 | `node_change_by_me`、`only_me_decides` |

### 吸收链路（Agent 维护层的目标）

AI 抽取建模成任意函数：同一个片段，两次运行可以给出完全不同的结果。下面的定理对任何抽取结果都成立。

| 性质 | 定理 |
|---|---|
| 吸收只产生通过检查的写入 | `ingest_reachable` |
| **只吸收新增**：新写进来的每一条，要么是记账（保存记录、吸收记录），要么是原件本身，要么出自这份原件里原文指纹以前没处理过的片段 | `ingest_only_new` |
| **覆盖检查**：吸收以后，每个片段都有处理结果 | `ingest_covers` |
| **幂等**：第一次吸收没有“未处理”的片段时，同一份输入再吸收一次，不管 AI 第二次抽出什么，内容都不再变化 | `ingest_idempotent` |

### 过目里的稿子（吸收链路 4、6，分析链路 3–5）

| 性质 | 定理 |
|---|---|
| 一个节点同时只有一份待定稿子：新的候选必须并进已有的那份 | `pending_unique` |
| 我拒绝过的内容（不要的稿子、确认时删掉的句子）此后不再被提出（按句子原文判断） | `rejected_never_reproposed` |
| 确认写进版本的稿子，确认时还在过目里，基于节点当时的最新版本 | `confirmed_draft_fresh` |
| 重新分析不改动出处是我的话的句子，除非我在逐句确认里单独决定 | `my_sentences_kept` |
| 稿子离开过目只有三种方式：被并进新稿子、我不要、我确认；不会悄悄消失 | `draft_leaves_review_only_by` |

### 重新吸收（吸收链路 · 重新吸收）

| 性质 | 定理 |
|---|---|
| 重新吸收只做 Agent 能做的写入，不动正文：所有版本、当前版本、有效 / 结束、所在的层都不变 | `reingest_body_untouched` |
| 这份原件之前产生的每条事实，要么已作废，要么它那项属性有待我裁决的冲突（作废被挡下，冲突留在过目里，不会被悄悄解决） | `reingest_voids_old` |
| 出处在这份原件里的有效节点都会列出来 | `reingestAffected_complete` |

### 删除（原始依据层 · 删除）

| 性质 | 定理 |
|---|---|
| 删除清单恰好是直接或间接依赖这份原件的所有写入，不漏也不多；因为存储层是 DAG，从旧到新扫一遍就能算完 | `affected_iff`、`deletionList_exact` |
| 删除只动内容：片段、出处、事实、版本都不变，出处指向删除记录，所有可追溯的定理照样成立 | `delete_keeps_structure` |
| 删除过的内容以后再存，内容恢复 | `ingest_restores_deleted` |

## 4. 形式化发现的问题和你的决定

前四条是检查里必须有的守卫。每条都有反例：关掉守卫时那条日志是合规的，但违反了对应的性质
（`MyLife/Counterexamples.lean`，用 `decide` 由 Lean 直接算出）。

| # | 问题 | 处理 | 反例 / 示例 |
|---|---|---|---|
| 1 | 单独移动一个被引用的节点，不加任何引用就打破“世界不引用个人” | **你的决定**：拒绝，列出挡住的引用者；你先改引用，或在同一次写入里把它们一起移 | `move_guard_needed`、`move_blockers_listed`、`group_move_ok` |
| 2 | 合并、分裂、换阶段时先新建再结束，中间会有同一问题两个有效节点 | 新建和结束旧节点在同一次写入里完成 | `atomic_end_needed`、`atomic_merge_ok` |
| 3 | 确认一份过时的稿子会悄悄覆盖中间的新版本 | 原设计已有，写进检查清单 | `cas_needed` |
| 4 | Agent 撤销抽取会悄悄替你裁决冲突 | **你的决定**：有待裁决的冲突时只有你能作废，Agent 的撤销进过目 | `void_guard_needed` |
| 5 | 定了权威作者以后，其他作者的不同值完全看不到 | **你的决定**：不提醒，但列成被盖过的说法，查得到 | `overridden_listed_example` |
| 6 | 作者标错了怎么办 | **你的决定**：双向都能更正，追加更正记录，受影响的句子和事实进过目 | `correction_flags_sentence` |
| 7 | 活视图里节点可以互相引用 | 允许（默认）；传播每层经过你，不会循环 | `live_graph_may_cycle` |
| 8 | 删除以后“出处指到存在的片段”不成立；同样内容再存会被当成已存过 | 出处改指删除记录；再存时恢复内容（默认） | — |
| 9 | 对话轮次按文本去重会误判 | 轮次指纹包含对话 id 和轮次 | — |

还有两点不需要你决定，但要知道：

* 节点身份是“它回答的问题”，机器判定不了。模型里用显式的问题键，唯一性定理相对于这个键成立；
  “是不是同一个问题”由你判断（设计里已经是“拿不准的交给我”）。事实的身份、同一笔钱同理。
* “我拒绝过的内容不再被提出”按句子原文判断：程序能拦住原样重复，换了说法的重复仍然要靠 Agent 读过目记录。

## 5. 不能形式化的部分

| 设计要求 | 为什么不能 | 模型里怎么处理 |
|---|---|---|
| 整理不增删观点、不改程度 | 涉及意思 | 只能保证一句一个出处、来源类别可推出；“列出改动的程度词、否定词、语气”可以做成程序，但词表是否完整不可证 |
| 程度标得对 | 涉及推理质量 | 只证明结构条件：AI 起草必标程度，“确定”必须引用事实或我的话 |
| 信息密度、不写废话 | 质量判断 | 不建模，靠过目 |
| AI 理解得对、抽取得对 | AI 输出不确定 | 抽取器建模成任意函数；定理对任何输出成立；理解错了靠重新吸收 |
| 属于世界还是个人（“去掉我还成立吗”） | 分类判断 | 层是节点的显式属性；分错了可以移，移层受守卫约束 |

## 6. 建模取舍

* 文字用指纹表示；“原话”近似为“句子文本和出处片段指纹相同”。
* 写入是顺序的。多个客户端同时写入时的竞争只体现在“稿子基于最新版本”这一条；更细的并发问题适合另用 TLA+ 建模。
* 还没建模：话题和分类、钩子、对象表和别名、同一笔钱、预期事实、界面装配。
  它们要么“分错没有后果”，要么是“推出的视图”或“只追加的记录”，加进来的方式和现有部分一样。
* 日志之外的地方（runtime 的索引和 embedding、Git 历史、备份）不在模型里；删除时由实现按删除清单去清理。

需要 Lean 4.15.0（`lean-toolchain` 已固定），不依赖 Mathlib：

# 安装 elan：https://github.com/leanprover/elan
cd mylife-formal
lake build        # 约 15 秒；会打印每条主要定理依赖的公理

## 8. 怎么用到实现上

* `CheckP` 就是“记录与检查”那一节的可执行版本，`design/CONTRACT.md` 是它的人话版本。
  实现里 MCP 写入前的检查应当和它一一对应，包括上面的四个守卫。
* 用这个模型当参考实现做差分测试：随机生成写入序列，同时喂给真实的 MCP 服务和 Lean 模型（`#eval` 可执行），
  比较“接受 / 拒绝”和推出的视图是否一致。
* 以后改设计时，先改模型、重新 `lake build`：哪条定理证不过了，就说明哪条性质被新设计打破，需要新的守卫或重新取舍。
